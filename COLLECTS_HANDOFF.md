## Общая идея фичи

RRR-CEP — CEP-панель для After Effects, порт старого ScriptUI-скрипта. Новая версия **RRR_3.0** получает блок **Collects**: пользователь вводит идентификатор креатива (например `MM.YY_AA_TaskName_video_V1,2,3`), система сама находит нужный архив ("коллект", `.aep`-файл) на Google **Shared Drive** (смонтирован локально через Google Drive Desktop, файлы могут быть недокачанными плейсхолдерами), вытаскивает из него запрошенные версии композиций и добавляет их в **текущий открытый** проект After Effects — полностью в фоне, не мешая работе пользователя, без лишних вложенных папок в результате (комп добавляется в корень, её ассеты — в существующие папки Audios/Comps/Images/layers/Videos текущего проекта), а в конце автоматически открывается диалог **Collect Files** для сборки мини-коллекта (только эта версия/разрешение) рядом с текущим проектом на диске.

Ключевые решения, принятые в разговоре:
- Прогресс — простой текстовый счётчик процентов скачивания архива (без графики, без списка/аккордеона). Несколько версий одного архива делят один счётчик. Несколько разных креативов качаются **параллельно**, без очереди/ожидания.
- Диалог Collect Files открывается **автоматически** сразу после готовности, с дефолтами "For Selected Comps" / "Reduce Project" / "Consolidate footage" — скриптового способа задать это гарантированно нет, полагаемся на то, что сами нужные композиции выделены (`.selected = true`) перед вызовом, и что AE помнит настройки диалога между запусками.
- Всё лишнее, что импортировалось вместе с архивом (другие версии/языки/папки), **удаляется** из текущего проекта после того, как нужные версии извлечены и разложены.
- Тяжёлая часть (поиск на Drive, докачка, извлечение нужной композиции из большого архива) должна идти **не в живой сессии AE**, а в фоновом headless-процессе — это было ключевое архитектурное решение, чтобы не мешать пользователю. См. ниже, что из этого подтвердилось, а что нет.

## Что опровергнуто / найдено во время спайка (ВАЖНО — меняет архитектуру)

Ключевая гипотеза плана была: гонять `aerender.exe` (headless-движок AE) с флагом `-s "<ExtendScript>"` для извлечения нужной композиции в фоне, невидимо. Проверка на реальной машине (AE 2026, `C:\Program Files\Adobe\Adobe After Effects 2026\Support Files\aerender.exe -help`) показала:

- **У `aerender.exe` НЕТ флага для выполнения произвольного ExtendScript.** Его `-s` — это "start frame" (номер кадра), не скрипт. `-comp`, `-RStemplate`, `-OMtemplate`, `-renderSettings` и т.д. — тоже не про запуск скрипта. Гипотеза №1 плана **неверна**, реализовывать по ней нельзя.
- `AfterFX.exe -s "<script>"` — **действительно** умеет выполнять скрипт (это подтверждённая, общеизвестная возможность полной GUI-версии), НО запуск `AfterFX.exe` — это **полноценное видимое окно** приложения, а не что-то скрытое/фоновое. Проверено на практике: случайный вызов `AfterFX.exe -help` (флаг не распознан) запустил обычный видимый пустой инстанс AE, который пришлось закрывать через `Stop-Process`.
- Единственный оставшийся кандидат на headless-запуск скрипта (без видимого окна) — **инъекция скрипта через `Support Files/Scripts/Startup` папку** (обнаружено, что правильное название папки — `Startup`, не `Startup Scripts`, как предполагалось в исходном плане: `C:\Program Files\Adobe\Adobe After Effects 2026\Support Files\Scripts\Startup`). Идея: `aerender.exe`, как консольный процесс без GUI, всё равно должен грузить обычный движок AE при старте — если он подхватывает те же Startup-скрипты, что и обычный AE, туда можно положить статический скрипт-диспетчер, который читает путь к нужному job-скрипту из переменной окружения процесса (`$.getenv(...)`) и делает `$.evalFile()`.
- **Это ещё не проверено.** Папка `Startup` защищена правами (`Program Files`) — запись туда потребовала бы UAC-элевации. Я спросил разрешения на разовую элевацию для теста, пользователь **не подтвердил и не отклонил явно** — вместо этого попросил перенести беседу на другую машину. **Это первый шаг, с которого нужно продолжить.**

# Collects (RRR_3.0) — фоновая подгрузка версий из архивов на Shared Drive

## Context

RRR-CEP — CEP-панель для After Effects (Bolt CEP: Vite + React + TS, ExtendScript-хост в `src/jsx/aeft/aeft.ts`), уже полностью содержащая логику кнопки **Collect** (`collectButtonClick`): переименование комп, сортировка по `Assets/{Audios,Comps,Images,layers,Videos}` + `<LANG>/<WxH>`, `reduceProject`, `consolidateFootage`, финальный нативный диалог "Collect Files...".

Компания архивирует такие же коллекты (по одному `.aep` на креатив, с той же внутренней структурой) на Google Shared Drive, смонтированный локально через Google Drive Desktop. Задача — новый блок **Collects**: пользователь вводит идентификатор креатива (например `MM.YY_AA_TaskName_video_V1,2,3`), система сама находит нужный архив на Drive, вытаскивает из него ровно запрошенные версии композиций и добавляет их в **текущий открытый** проект — полностью в фоне, не мешая работе, без вложенных папок в результате, с автоматической сборкой мини-коллекта той же версии рядом с текущим проектом в конце.

Ветка `feature/collects` уже создана и активна в `RRR-CEP`; релизы/автообновление продолжают собираться только из `main`.

**(См. раздел выше "Что опровергнуто" — ключевое архитектурное решение из следующего абзаца нуждается в пересмотре по итогам спайка.)**

Ключевое архитектурное решение (согласовано с пользователем): тяжёлая часть (поиск на Drive, докачка файлов-плейсхолдеров, извлечение нужной композиции из большого архива) выполняется **не в живой сессии AE**, а в headless-процессе `aerender.exe` (консольный движок AE без UI, обычно используемый рендер-фермами) — это гарантирует, что живой проект пользователя вообще не трогается, пока идёт долгая часть работы. Только в самом конце — короткий, почти мгновенный вызов в живую сессию: импорт уже урезанного мини-проекта + один системный диалог "Collect Files..." (его нельзя убрать — ограничение самого AE, уже принято пользователем и так же используется в текущей кнопке Collect).

## Архитектура пайплайна

```
[Панель, Node/React]                          [aerender.exe, headless]          [Живая AE-сессия, ExtendScript]
input "MM.YY_AA_TaskName_video_V1,2,3"
  → parseCollectRequest()
  → findCollectFile() на Shared Drive
  → hydrateWithProgress()  (% в UI) ────┐
                                        │
                     spawn aerender ────┴──→ найти V1/V2/V3 в архиве
                                              consolidateFootage + reduceProject
                                              save(tempProject.aep) + манифест
  ← читает манифест/temp .aep ──────────────────────┘
  → evalTS("prepareCollectImport", tempPath, compNames, lang) ─────────────→ импорт tempProject как FolderItem
                                                                              разложить keep-items по существующим
                                                                              папкам текущего проекта (reuse-or-create)
                                                                              удалить всё остальное импортированное
                                                                              select только нужные композиции
  → evalTS("triggerCollectFilesDialog") ──────────────────────────────────→ findMenuCommandId + executeCommand
                                                                              (один клик пользователя, как сейчас у Collect)
```

Несколько разных креативов запускаются параллельно (без очереди/ожидания) — каждый свой `aerender`-процесс. Несколько версий ОДНОГО архива используют один и тот же `.aep`, поэтому докачка/поиск на них общие, с одним счётчиком прогресса.

## 1. Парсинг идентификатора — `src/js/lib/collects/parseCollectRequest.ts`

Чистая функция без зависимостей от Node/cep (легко тестируется отдельно):

```ts
export type ParsedCollectRequest = {
  projectName: string;   // например "07.26_AA_SummerPromo" — просто префикс, без строгой валидации формата
  versions: number[];    // [1,2,3], дедуп + сортировка, минимум 1 элемент
  resolution: { w: number; h: number }; // всегда {1080,1920} — несовпадение = явная ошибка, не молчаливая коррекция
  language: string;      // по умолчанию "EN"
};
export type ParseResult = { ok: true; value: ParsedCollectRequest } | { ok: false; error: string };
export function parseCollectRequest(input: string): ParseResult
```

Логика: найти токен версии `/_[Vv](\d+(?:\s*,\s*\d+)*)\b/` (обязателен — без него явная ошибка, не дефолт на V1, т.к. имена полностью формульные и молчаливый дефолт замаскирует опечатку); всё до него (минус необязательный `_video`) — `projectName`; после — необязательные `WxH` (несовпадение с 1080×1920 → ошибка) и язык (искать 2-буквенный код из уже существующего списка `LANG_CODES`, `src/js/main/main.tsx:29` — переиспользовать этот массив, а не дублировать). Покрыть регистронезависимость, пробелы вокруг запятых, полное имя рендер-файла (`..._20s_EN_Nick`) и короткую форму.

## 2. Поиск на Shared Drive — `src/js/lib/collects/driveSearch.ts`

Корень Shared Drive хранится через **тот же паттерн настроек**, что уже используется для имени автора (`app.settings` в ExtendScript, не localStorage — в проекте нет браузерного persistence вообще). Добавить в `aeft.ts` `getSavedCollectsRoot()`/`saveCollectsRoot(path)` по образцу `getSavedCreatorName`/`saveCreatorName` (см. `aeft.ts`, секция настроек). Node-сторона запрашивает через `evalTS`, при отсутствии — `window.prompt` один раз (как для имени автора в `main.tsx:46-56`), сохраняет.

`findCollectFile(root, projectName): Promise<string | null>` — обход `fs.promises.readdir` (асинхронно, **не** `*Sync` — в отличие от `update.ts`, здесь листинг может реально зависать на сетевых операциях облачного диска, и синхронный вызов заморозил бы всю панель, т.к. Node работает in-process с рендерером панели через `--enable-nodejs`/`--mixed-context`). Точное совпадение по префиксу `projectName` (не нечёткий поиск — пользователь подтвердил, что имена полностью формульные), с ограничением глубины/числа посещённых папок, чтобы плохой случай не подвесил поиск навсегда. Если найдено несколько — берём с самым свежим `mtimeMs`.

## 3. Докачка плейсхолдера + процент — `src/js/lib/collects/hydrate.ts`

Файлы на Shared Drive в режиме "по требованию" — чтение через `fs.createReadStream` прозрачно триггерит скачивание реальных байт. Считаем прогресс по факту прочитанных байт относительно `fs.stat().size`:

```ts
export function hydrateWithProgress(filePath: string, onProgress: (pct: number) => void): Promise<void>
```

С watchdog (нет `data`-события 60 секунд → ошибка "скачивание зависло"), не с фиксированным общим таймаутом (большие файлы легитимно долго качаются). Прогресс общий на уровне пути к файлу (`Map<absPath, {promise, subscribers}>`) — если несколько версий или несколько одновременных запросов ссылаются на один и тот же `.aep`, они автоматически делят один прогресс, без отдельного UI-кода для этого случая.

**Открытый вопрос для проверки на практике**: `reduceProject`/`save` не трогают байты футажей напрямую, но неизвестно, не тянет ли AE при открытии проекта что-то из папки `(Footage)` рядом (превью/пробы цвета) даже для плейсхолдеров. Проверить эмпирически на реальном архиве с недокачанными футажами в начале реализации — если тянет, докачивать `(Footage)` параллельно тем же механизмом.

## 4. Параллельность и UI

Без очереди — каждый ввод сразу запускает независимый `runCollectRequest()` (не await'ится в UI), каждый со своим `child_process.spawn` (не `execSync` — чтобы не блокировать). N одновременных креативов = N процессов, без явного планировщика.

UI — **без списка/аккордеона** (пользователь явно отказался от этого в пользу простого счётчика): новая строка под текущим рядом кнопок в `main.tsx` (`CollectsRequestBar.tsx`, по аналогии с уже вынесенным `IconButton.tsx`) — поле ввода (Enter = отправить, как для custom-lang инпута, `main.tsx:211-223`) и под ним по одной текстовой строке на каждый активный запрос вида `"<ввод> — 63%"` / `"— извлечение…"` / `"— готово"` / `"— ошибка: …"`, которая исчезает через несколько секунд после готовности. Это моя трактовка "просто счётчик процентов, без графики" применительно к параллельным запросам — по одной строке на активный, не на завершённые.

Стили — в существующий `src/js/main/main.scss` (не заводить отдельный файл ради ~20 строк), используя `$error` из `variables.scss` для ошибок.

## 5. Извлечение через фоновый headless-процесс — `src/js/lib/collects/aerender.ts`

**ЭТОТ РАЗДЕЛ ТРЕБУЕТ ПЕРЕСМОТРА** по итогам спайка (см. "Что опровергнуто" выше). Исходный "рекомендуемый путь" через `aerender -s "$.evalFile(...)"` **невалиден** — у `aerender` нет такого флага. Продолжать со Startup-скрипт-диспетчером (изначально помеченным как fallback) как единственным кандидатом, либо пересматривать архитектуру целиком, если и он не сработает.

**Путь к бинарнику**: через новый `getHostExePath()` в `aeft.ts` (`app.exePath`, если недоступно — fallback на `csi.hostEnvironment.appVersion` + скан `Program Files\Adobe\`), затем `path.join(path.dirname(exePath), "aerender.exe")` — гарантированно та же версия AE, что и запущена, без догадок про CEP 11 vs 12. (Подтверждено на практике: у AE 2026 бинарник лежит в `Support Files\aerender.exe`, `Support Files\AfterFX.exe`.)

**Startup-скрипт-диспетчер (теперь основной, а не запасной путь, — требует подтверждения работоспособности):** установить один раз (с явным запросом на elevation, как уже реализовано в `update.ts` через `elevateAndCopyDir`/PowerShell `-Verb RunAs`) статический скрипт-диспетчер в `Support Files/Scripts/Startup/` (точное имя папки подтверждено на практике — НЕ "Startup Scripts"), который читает путь к job-скрипту из переменной окружения (`$.getenv("RRR_COLLECT_JOB_JSX")`, задаётся per-process через `child_process.spawn(..., {env})`) и делает `$.evalFile()`.

Результат job передаётся не через код возврата процесса (ненадёжно для headless AE), а через **манифест-файл** (`{ok, tempProjectPath, extractedCompNames}` или `{ok:false, error}`), который Node читает после завершения процесса; таймаут ~5 минут с принудительным `kill`.

`spawn(..., { windowsHide: true })` — не показывать даже консольное окно.

**Если Startup-диспетчер тоже не сработает** — вернуться к пользователю с пересмотром: либо смириться с кратким видимым окном `AfterFX.exe -s` (нарушает "невидимо", но рабочий вариант), либо отказаться от отдельного headless-процесса и переделать пайплайн так, чтобы все шаги (поиск, докачка) оставались в Node/панели как и раньше, а извлечение/reduce делать прямо в живой сессии короткими `evalTS`-вызовами вместо отдельного файла — с осознанием, что это будет короткие, но заметные подвисания живой сессии на время обработки большого архива.

## 6. ExtendScript-хост (`src/jsx/aeft/aeft.ts`)

### 6.1 Рефакторинг `organizeProjectForCollect` (строки 7-93) для переиспользования

Сейчас функция всегда создаёт папки заново (`addFolder`, строки 11-15/42-47) и всегда сканирует **весь** проект (`proj.numItems`, строки 66-67) — оба поведения корректны для существующего вызова из `collectButtonClick` (там весь проект и есть то, что собирается), но недопустимы против **живого** проекта пользователя (нельзя ни плодить дублирующиеся `Assets`-папки, ни трогать чужой контент). Решение — чистый extract-and-parameterize без изменения поведения текущего вызова:

- `getOrCreateCollectFolders(parent)` — то же самое, но через уже существующий reuse-safe `getOrCreateFolder` (строка 393) вместо `proj.items.addFolder`.
- `classifyItemForCollect(item, selectedCompLangs, folders)` — та же ветка switch (строки 74-91) как отдельная функция от одного item.
- `organizeProjectForCollect(proj, selectedCompLangs)` — существующий вызов из `collectButtonClick`, поведение не меняется (весь проект, folders от `proj.rootFolder`).
- **Новая** `organizeImportedItemsForCollect(proj, items, selectedCompLangs)` — тот же `classifyItemForCollect`, но по явному списку `items` (только то, что реально импортировали и решили оставить), never re-scan `proj.numItems`.

### 6.2 Поиск версии внутри архива (используется только headless-скриптом, не через `evalTS`)

```ts
function findCollectVersionComps(proj: Project, wanted: {versions:number[]; lang?:string}): CompItem[]
```

Обход `<LANG>`-папок в корне (фильтр по `LANGUAGES`, строки 96-110) → `<WxH>`-подпапок → комп с именем, строго соответствующим `^V(\d+)__(\d+)x(\d+)_([A-Za-z]{2})$` (паттерн из `buildProjectName`, строка 370-372 + суффикс языка). Строгий якорный паттерн обязателен — рыхлый `getVersionFromName` (строка 339-342, `/[Vv](\d+)/`) также матчит вложенные precomp-версии из `duplicateCompVersionGraph` (строка ~448), которые не являются корневыми версиями.

Дальше в headless-скрипте: `proj.consolidateFootage(); proj.reduceProject(targetComps); proj.save(new File(outputTempPath));` — те же вызовы, что уже в `collectButtonClick` (строки 1224/1227), плюс запись манифеста с именами извлечённых комп.

**Headless-ограничения, обязательные к соблюдению в этом скрипте**: никаких `alert()` (несколько существующих хелперов их вызывают — не переиспользовать их в headless-пути без аудита), никакого `saveWithDialog()` (только `save(file)` с явным путём — не показывает диалог), никакого `findMenuCommandId`/`executeCommand` (это только для живой сессии, шаг 6.4).

### 6.3 `prepareCollectImport` — новая экспортируемая функция

```ts
export function prepareCollectImport(
  tempProjectPath: string,
  targetCompNames: string[],
  fallbackLang: string
): { ok: boolean; keptCompNames: string[]; missingCompNames: string[]; message?: string }
```

Шаги (один `beginUndoGroup`/`endUndoGroup`, по образцу `collectButtonClick`):
1. `proj.importFile(new ImportOptions(new File(tempProjectPath)))` с `importAs = ImportAsType.PROJECT` (подтверждено в `types-for-adobe/AfterEffects/22.0/index.d.ts:459` и `:1819`) → получить `FolderItem` импорта, принудительно `parentFolder = proj.rootFolder`.
2. Рекурсивно собрать всё под этой веткой (новый `collectAllDescendantItems` — обобщение уже существующего `collectSourceItems`, строки 138-151, но с захватом и `FootageItem`, не только `FolderItem`/`CompItem`).
3. Найти корневые target-композиции по `targetCompNames`; если пусто — почистить импорт и вернуть `ok:false`.
4. Построить keep-set: `collectCompGraph` (уже существует, строки 414-432, без изменений) для вложенных комп + новый `collectFootageDependencies` (по аналогии, но `layer.source instanceof FootageItem`) для футажей.
5. Язык каждой keep-композиции — через уже существующий надёжный `extractLanguageCodeFromName` (строка 122-126) по имени, а не по иерархии папок (папки сейчас будут удалены).
6. `organizeImportedItemsForCollect(proj, keepItems, langs)` (6.1) — раскладка в СУЩЕСТВУЮЩИЕ папки текущего проекта.
7. Удалить всё, что не попало в keep-set: `item.remove()` напрямую, затем те же две прохода reparent-to-root-then-remove, что уже в `collectButtonClick` (строки 1213-1221), но по явному списку папок импорта (не по всему проекту).
8. Выставить `.selected = true` только на keep-композиции, `false` — на всё остальное в проекте (`Project.selection` — readonly, поэтому только через `Item.selected`).
9. Вернуть результат.

### 6.4 `triggerCollectFilesDialog` — отдельная экспортируемая функция

Существующий блок (строки 1250-1256) вынести в приватный `triggerNativeCollectFilesCommand()`, вызывать и из `collectButtonClick` (без изменения поведения), и из новой `export function triggerCollectFilesDialog()`. Отдельно от `prepareCollectImport`, чтобы панель могла различать "импорт готов" от "пользователь закрыл диалог", и чтобы шаг был независимо тестируем.

По поводу дефолтов диалога (For Selected Comps / Reduce Project / Consolidate footage) — **скриптового способа задать их нет** (принятая пользователем оговорка); корректный `.selected` на нужных компах (шаг 6.3.8) — единственный доступный рычаг влияния, плюс расчёт на то, что AE помнит последние использованные настройки диалога между запусками как настройку приложения (проверить эмпирически, зафиксировав руками один раз).

## Риски / что проверить эмпирически перед/во время реализации (в порядке важности)

1. ~~`aerender -s "$.evalFile(...)"` реально исполняет ExtendScript headless~~ — **ОПРОВЕРГНУТО**, флага нет. Заменить на: **Startup-скрипт-диспетчер в `Support Files/Scripts/Startup/` реально подхватывается `aerender.exe` при старте** — ключевое неподтверждённое допущение теперь.
2. **`consolidateFootage`/`reduceProject`/`save(file)` работают в headless-движке aerender идентично интерактивному** — только `save(file)` (не `saveWithDialog`) гарантированно бездиалоговый по документации; остальное не подтверждено из исходников.
3. **Реакция AE на плейсхолдеры футажей при открытии проекта** (раздел 3) — не тянет ли AE байты футажей уже на открытии, а не только на `reduceProject`/копировании.
4. **Поведение `importFile`/`ImportAsType.PROJECT`** при коллизии имён с уже существующими в живом проекте папками/итемами (например если в текущем проекте уже есть папка "EN") — не подтверждено из исходников, требует теста на реальном архиве.
5. **Возможный диалог "missing footage" при импорте** временного мини-проекта, если пути футажей не резолвятся в контексте живой сессии — если возникает, ломает "без лишних диалогов".
6. **Персистентность настроек диалога Collect Files** ("For Selected Comps"/Reduce Project/Consolidate) между запусками — нет API, только надежда на память самого приложения; фоллбэка нет, пользователь это принял.
7. Уникальность временных путей (`tempProjectPath` с GUID) — на стороне Node, чтобы `proj.save()` не затирал чужой job.
